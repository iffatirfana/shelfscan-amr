# Retraining the detector for the code-labelled world — v3 and v4

**Status: closed, negative result. Neither v3 nor v4 beats v2; work stopped
here.** Nothing in this line of work feeds the submission: `results/`,
`results_v2/`, `models_v2/`, the original 30-seed evaluation and
`docs/ShelfScan_submission.pdf` are untouched. It all lives on the
`ml-extras` branch and has not been pushed.

This picks up the last open question in [MVP_LABELS.md](MVP_LABELS.md): the
code-labelled world loses slot accuracy against the printed-pattern world
because a blocked carton's code cannot be read and the SKU gate deliberately
forbids the detector from guessing one. The suggested fix there was to
"retrain the detector on code-labelled cartons so the fallback is trustworthy
again". Two attempts at that are recorded below.

## The three detectors

| | classes | train / val frames | what else changed |
|---|---|---|---|
| **v2** | `sku_A..sku_D, slot_empty, blocker` | the original printed-pattern set | baseline; the audit's fallback detector |
| **v3** | `cardboard_box, label, slot_empty, blocker` | 797 / 234 | SKUs collapse into one carton class (the code carries the SKU, not the carton's look); the code plate becomes its own class so the audit can crop it before decoding. Shipped with a 3-scale crop decode cascade and a whole-frame fallback. |
| **v4** | same four | 1109 / 286 | v3's dataset plus 364 targeted frames of empty bays behind a blocker, and `slot_empty` labelled down to `vis >= 0.35` instead of `0.70` |

In every row the audit is V4_active on seeds 101-110, HUD unset, and the SKU
safety gate is in force: in label mode the detector never supplies a SKU.

## What went wrong in v3, and what v4 did about it

Of 600 slots, v3 differed from v2 on 10, and 8 of those were v3 answering
UNVERIFIED where v2 had been correct. They were the same four slots seen in
both label worlds, all **genuinely empty bays with a pallet in front of
them**. The raw detector output (`SHELFSCAN_DEBUG_BOXES=1`) showed `blocker`
firing at 0.93-0.97 with its centre inside the slot box in every frame, while
`slot_empty` was absent entirely in half of them and reached only 0.27-0.39
in the rest, against a 0.60 gate. Not a threshold problem — a missing-class
problem.

The cause was in the capture script, not the model. `cardboard_box` was
labelled down to `vis >= 0.35` and `label` to `0.50`, but `slot_empty`
required `0.70`. A bay half hidden behind a pallet therefore had its
`blocker` box written and its `slot_empty` box dropped — a frame that asserts
the right answer for a blocked empty bay is "blocker". That is what v3
learned.

v4 made the rule a knob (`SHELFSCAN_EMPTY_VIS`, default unchanged at 0.70),
captured at 0.35, and added a `--capture-only empty_blocked` filter so a seed
drives to only its empty-and-blocked slots. 62 seeds drawn from 15-100 and
131-168 — none from the eval range 101-130, none from dev 13-14 — yielded 364
frames.

| | v3 train | v4 train | v3 val | v4 val |
|---|---|---|---|---|
| frames | 797 | 1109 | 234 | 286 |
| `slot_empty` boxes | 159 | 400 | 15 | 55 |
| frames with `slot_empty` **and** `blocker` | 32 | 273 | 3 | 43 |

v4 validation: `slot_empty` P 0.838 / R 0.982 / mAP50 0.945 over 55 instances.
v3 reported R 1.00 — over 15 instances in 3 blocked-empty frames, a set too
small to see the failure mode at all. That is the more useful lesson here than
either model: **v3's validation score could not have caught v3's defect.**

## The trade v4 actually made

It fixed what it was aimed at:

| physically-empty bays, correct final status | v2 | v3 | v4 |
|---|---|---|---|
| unobstructed | 35/35 | 35/35 | 35/35 |
| behind a blocker | 5/6 | 1/6 | 4/6 |

and the UNVERIFIED regression v3 opened is gone. But the same change moved the
error to the other side of the gate:

| occupied bays wrongly called EMPTY | v2 | v3 | v4 |
|---|---|---|---|
| QR | 1 | 0 | 2 |
| Code128 | 1 | 1 | 2 |

All four are the same shape — a carton seen past a **right-hand carton
blocker**, with `slot_empty` firing at **0.66-0.72** against the 0.60 gate
(seeds 106 S1-0-2 and 109 S0-0-4 on QR; 109 S0-0-4 and 110 S1-2-3 on
Code128). This is val precision 0.838 showing up in the audit. The
expectation that the audit's own `vis >= 0.70` gate would absorb it was
wrong: these clear both gates.

Net slot accuracy is a tie. **The two sides of the trade are not worth the
same, though.** An UNVERIFIED asks the operator for another look; a false
EMPTY dispatches someone to restock a bay that is full, and in the seed 110
case it overwrote a real MISPLACED. That is why this is recorded as a loss
rather than a wash.

## Why it stops here

Teaching `slot_empty` to fire through occlusion also taught it to fire through
a carton that merely looks occluded: a 0.35 labelling floor does not
distinguish "empty bay, partly hidden" from "full bay, mostly hidden".

The obvious next move is a one-line, no-retrain change — raise the audit's
`slot_empty` confidence gate from 0.60 toward ~0.75, which would drop all four
false EMPTYs (0.66-0.72) while keeping the blocked-empty recoveries
(0.83-0.86). It is not done, because picking that number from the four slots
in the eval set is fitting to the test set. Doing it honestly needs dev-seed
data, and dev seeds 13-14 hold one qualifying slot between them, so it would
need its own capture run first. There was no time to collect that safely
before the deadline, so no threshold was tuned and no further model trained.

Also untried, and the more promising direction if this is ever resumed: give
the capture an explicit `occluded_content` signal rather than inferring
emptiness from a visibility fraction, so the two cases are separable at
labelling time instead of being asked of the model.

## Reproducing

```
# dataset (datasets_v4 and models_v4 are gitignored; both regenerate)
# CAP is the 62 seeds in 15-100,131-168 that hold at least one empty-and-
# blocked slot; the rest are skipped before Webots starts. VAL is the 8 of
# them held out. Neither list touches 101-130 or dev 13-14.
CAP=17,18,19,21,22,23,24,28,29,36,37,39,41,42,45,46,48,49,55,57,62,63,64,65,\
67,68,69,72,73,75,82,83,84,87,89,93,94,95,96,97,99,100,131,132,138,139,140,\
141,142,143,145,149,151,152,153,157,158,159,161,163,167,168
VAL=24,42,62,72,89,100,142,157
python experiments/run_batch.py capture --seeds "$CAP" --val-seeds "$VAL" \
    --classes v3 --label qr --capture-only empty_blocked --empty-vis 0.35 \
    --out datasets_v4 --jobs 4 --timeout 600
python train/train_yolo.py --data datasets_v4 --classes v3 --epochs 30 \
    --imgsz 320 --device cpu --project models_v4 --name yolov8n_v4

# evaluation (HUD unset; ~10 min per label type)
python experiments/run_batch.py eval --seeds 101-110 --policies V4_active \
    --label qr --classes v3 --seedwise --no-rendering --timeout 900 \
    --results results_v4/qr --weights <abs>/models_v4/yolov8n_v4/weights/best.pt
```

30 epochs on 1109 frames at 320 px took 1.11 h on this machine's CPU; there is
no CUDA GPU here.

## The demo visuals are gated, not applied

v4 is sensitive to the racking it was trained against, which constrains what
the recording may change. The demo pass of 2026-11-26 repainted the racking
galvanised grey and closed the back of the bay-mouth pallet. Re-running the
audit on seeds 101-104 (QR, HUD unset) against the committed v4 results: 119
of 120 slots identical, 89 of 89 codes decoded identically, 104 of 120 correct
either way. The one slot that moved was **103 S1-0-1** — a bay really holding
`sku_B` behind a right-hand carton blocker — UNVERIFIED before, EMPTY at conf
0.71 after. Accuracy is unchanged, because both answers are wrong, but the
error got worse in the way this document argues matters most: a slot that
admitted it did not know now asserts a full bay is empty.

That is the same failure mode as the four false EMPTYs above, and the cause is
mundane: every training frame in `datasets_v4` was captured against the
blue-and-orange world, so repainting the racking changes the detector's input.
A pallet blocker stands in 25 of the 300 slots of seeds 101-110, so the closed
pallet back is an input change too, and it is gated alongside the paint rather
than kept.

So both live behind `make_world --demo` / `wbt(demo=True)` (`DEMO_PALETTE`),
off by default:

- **Measured runs** get the world v4 was trained on. `experiments/run_batch.py`
  calls `wbt(lay, version, controller)` with three positional arguments, so it
  cannot reach the flag, and `--demo` is deliberately not implied by
  `--display` — a `HUD_DISPLAY=1` debugging run on an eval seed still renders
  the trained-on world.
- **The recording** gets the better-looking one, built with `--demo`.

Verified by generating seeds 101-110 both ways and comparing the world text:
the default build is byte-identical to the pre-recolour world the v4 numbers
were measured on, apart from the two appearance `DEF`s being renamed
`RACK_BLUE`/`RACK_ORANGE` → `RACK_UPRIGHT`/`RACK_BEAM` (named for the section
so the names stay honest under either paint), and the `--demo` build is
byte-identical to what the recolour commit produced. Webots renders from
`baseColor` and geometry, not `DEF` names, so eval frames are unchanged and
the 103 S1-0-1 regression cannot occur in a measured run.
